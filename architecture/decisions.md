# Foundation Decisions

The decisions that define the architecture, and why they were made. For how the architecture works today, start with the [Architecture Overview](../architecture/overview.md).

Some decisions use older names: **Engine** is now the Agent Loop, **Provider API** is now the Model API, and **connectors** are now the two APIs. Numbers have gaps because product-level decisions are tracked by each implementation, not here.

| # | Decision | Rationale |
|---|----------|-----------|
| D15 | Product clients are product-owned, not coupled to the Engine | The client is the product's brand. Decoupling from the Engine means the product controls the experience AND the client is swappable. |
| D16 | Zero custom protocols — use the prevailing industry standard, not a proprietary one | Never invent a protocol when an existing one will do. Swappable via adapter when the standard shifts. |
| D20 | Client metadata flows through the Gateway API contract | Client sends context, Gateway passes it through, Engine uses it. |
| D22 | Auth on both local and managed hosting | Auth is a memory concern (who can access your system), not a hosting concern. |
| D23 | Managed hosting is stricter, not just easier (superseded by D148 and D171: hosting is outside the architecture) | Same code, different configuration. Managed hosting restricts tool access and enforces policies through configuration, not code forks. |
| D24 | Engine ceiling must match the leading agent tools | The architecture must never be the bottleneck. If the Engine caps out, we swap it — because the contracts make that possible. |
| D26 | Skill execution = multi-turn, adaptive, judgment-based | Skills are NOT scripts. The model must support real agentic behavior. This is the minimum bar. |
| D39 | The Engine is a generic agent loop with no product-specific logic | Composability. A generic engine picks up any tool. A domain-specific engine only picks up domain-shaped things. |
| D40 | Prompt assembly and skill execution live in Memory, not the Engine | Product behavior emerges from what's in the files, not from custom engine code. |
| D51 | Tools are not a component — they are capabilities in the environment | Every concern maps to existing components: definitions in Memory, execution in Engine, permissions in Auth. |
| D53 | Tool Protocol connector is not needed — tool calls flow through the Provider API | No gap between the Provider API and the Engine's execution. Two connectors, not three. |
| D57 | The client is not a component — it's any external client | The system is Your Memory + Engine + Auth + Gateway. Clients connect to it through the Gateway API. |
| D58 | Gateway is a new component — manages conversations and routes to the Engine | Without the Gateway, conversation management would violate Engine genericity (D39) or Memory unopinionatedness (D43). |
| D60 | Auth is a cross-cutting layer — independent of the Gateway | Auth and the Gateway can each be swapped on its own. The Gateway calls Auth only through the Auth contract (D176), so neither depends on how the other is built. |
| D63 | Models are not a component — they are external intelligence | The system calls a model through the Provider API. It doesn't contain one. |
| D64 | Four components, two connectors, three external dependencies | The final architecture resolved through six component interviews. |
| D65 | A product built on the architecture is composable lego blocks — each piece independently usable | A product is a box of legos, not a monolith. No piece requires another piece. |
| D135 | Memory/tool binary — if it's data, it's memory; if it's not data, it's a tool | Everything is either a noun (memory) or a verb (tool). New capabilities compose from existing primitives. "Your Memory" (D138) distinguishes the component from the concept. |
| D137 | Gateway ↔ Engine is a plain HTTP API contract — not a third connector | One internal endpoint between two components we control. See [gateway-agent-loop-contract.md](../architecture/gateway-agent-loop-contract.md). |
| D138 | Memory component renamed to "Your Memory" | Distinguishes the component (your owned local storage) from the concept (all data is memory per D135). |
| D139 | Contracts are swappable via adapters — completing zero-lock-in | Components via contracts, contracts via adapters, Memory via tools. The swappability chain is structurally complete. See [adapter-spec.md](../architecture/adapter-spec.md). |
| D143 | Configuration is a cross-cutting concern with its own spec | Not owned by any single component. Three categories: preferences (Your Memory), runtime config (thin bootstrap), tool self-description. See [configuration-spec.md](./configuration-spec.md). |
| D148 | The architecture defines local deployment only — managed hosting is a product offering | The foundation defines how the system runs on hardware the owner controls. Managed hosting is a product offering layered on top. See [deployment-spec.md](./deployment-spec.md). |
| D147 | Anti-lock-in CI test — three swaps must succeed with config-only changes | Provider swap, model swap, tool swap. If any requires code changes, lock-in has been introduced. CI-testable on every release. |
| D170 | A re-created identity gets no access until the owner turns it back on | After an export and import, policies for unknown identities stay dormant. Access is never granted silently. How the owner restores access is up to each product. See [auth-spec.md](./auth-spec.md). |
| D171 | On the owner's own hardware, the owner has the last word | Products ship defaults the owner can change. No product rule overrides the owner locally. Rules the owner can't override belong to hosting, which the architecture doesn't cover. See [configuration-spec.md](./configuration-spec.md). |
| D172 | Secrets live outside Your Memory and are never tracked by git | Environment variables, an untracked config file and a secret store all qualify. Exporting Your Memory can never leak a key. See [security-spec.md](./security-spec.md). |
| D173 | Containers are one supported way to run the system, not the default | Packaging is an implementation choice. The architecture must run with no licence activation. See [deployment-spec.md](./deployment-spec.md). |
| D174 | The specs state requirements, not screens or hosting rules | Products decide when and how to show things to the owner, and how they host. |
| D175 | The model travels with each request | The Gateway reads the owner's current model choice on every message and passes it to the Agent Loop, so the next message uses the new model with no restart. |
| D176 | The Gateway calls Auth on every request, and the Agent Loop asks Auth before each tool call | One place for every access decision. Permissions live only in Auth. Auth stays swappable behind its contract. See [auth-spec.md](./auth-spec.md). |
| D177 | The default policy is that the owner can do everything | Approval prompts are a product choice, not an architecture default. |
| D178 | One message shape across the Gateway API, the internal contract and the Model API | Tool calls and tool results are normal parts of messages and are saved in conversation history, so a conversation can be replayed and moved faithfully. |
| D179 | Message content is a list of parts | Text first, with room for images and files, so content can grow without breaking the contracts. |
| D180 | Version history and restore are required for Your Memory | How they are built is up to each implementation. Git is one option. See [memory-spec.md](./memory-spec.md). |
| D181 | The architecture's product spec lives in this repository | User stories and acceptance criteria sit beside the specs that serve them. See [the PAA spec](../spec/personal-ai-architecture-spec.md). |
| D182 | Conformance tests are language-neutral and every implementation and template must pass them | Anyone can build the architecture in any language, from the specs alone or from a template. The tests are what prove it is still the architecture. |
| D183 | The test suite is named the PAA conformance validator | Dave J's term, agreed on the 2026-10-21 dev call; it replaces "conformance kit". Use the full name once, then "the validator". A system that passes is PAA-conformant; the individual checks stay "conformance tests". See [paa-conformance-validator](https://github.com/Personal-AI-Architecture/paa-conformance-validator). |
| D184 | The repository serves four visitors: someone who wants to understand PAA, a developer building a system, an AI coding agent doing that build, and someone verifying a system built on PAA | Verification means running the validator against the system's PAA interfaces for a pass or fail; an AI review never decides conformance, and a system that does not implement the PAA contracts cannot be validated. The zero lock-in checklist stays a self-assessment guide. Narrow, specific AI check prompts (for example, trace a message from the owner to the model and back) may sit beside the validator as aids. |
| D185 | The repository moves to top-level folders named for each visitor's job, each marked binding or derived | `spec/`, `architecture/` (with `background/`), `contracts/`, `conformance/`, `build/`, `maintainers/` and `assets/`. The GitHub front page then explains itself, and derived material in `build/` never competes with the binding specs. Dave J does the move first, then the contract revisions. |
| D186 | PAA v1.0 is done when six things are true | (1) Every v1 acceptance criterion passes or is changed by an explicit decision, and no gap blocks v1. (2) The contracts are frozen to these decisions. (3) The repository checks pass on a fresh clone. (4) The validator runs and every template passes it. (5) A fresh coding agent given the tagged repository and a template builds the minimal system, and it passes the validator. (6) Both maintainers sign off, v1.0 is tagged, and the website points at it. |
| D187 | The Gateway serializes messages within one conversation | A conversation has one active Agent Loop turn at a time. Later messages queue in arrival order until the active turn reaches a terminal `done` or `error` state; different conversations may run concurrently. This prevents ambiguous history ordering while allowing any client to resume a conversation. |
| D188 | A provider failure is reported, not automatically recovered by fallback | The Agent Loop emits the canonical provider error and stops the current turn. Automatic selection of another provider is not a PAA requirement; a product or implementation may offer an explicit retry or provider-change action outside the current turn. PAA defines no fallback model: an owner-set fallback is too complex, and an unset one would mean choosing a model and sending the owner's data for them. |
| D189 | The Gateway records a failed turn as an incomplete turn | The incoming message is persisted before dispatch when possible. Observed assistant text, tool calls, tool results and the terminal error are retained as partial history; no failed turn is reported as complete. If the initial persistence fails, the Gateway does not dispatch the request and reports the storage error. |
| D190 | In v1 the AI acts under the owner's identity; agent identities are deferred to the agents step | Every v1 tool call is internal, on the owner's own memory, so the authenticated actor for a conversation is the owner, and approval prompts stay a product choice. Distinct identities for AI agents acting for the owner, and how that delegation appears in Auth checks and audit records, are decided when PAA adds external tool calls or external agents (GAP-PAA-24). |
| D191 | Revocation cancels an active Agent Loop turn through the internal contract | The Gateway targets the active request by correlation ID at `POST /agent-loop/cancel`. The Agent Loop cooperatively cancels supported in-flight work, starts no further model or tool work, emits `auth_error`, and does not permit retry under the revoked context. |
| D193 | The active provider is an owner preference, read on every message like the model | An adapter config may list several provider profiles (for example BrainDrive Models, OpenRouter and Ollama), each naming its endpoint and a secret reference, never a key. The active profile is an owner preference in Your Memory beside the model choice; the Gateway reads both on every message and passes them to the Agent Loop, so switching provider needs no restart. A restart stays allowed only when a new kind of adapter (a new format) is installed. Choosing a model per task within one conversation stays out of scope (GAP-PAA-26, adopted on the 2026-10-22 dev call from BrainDrive's reference build). |
| D194 | Every saved assistant reply records the model and provider that produced it | The owner can always see which company processed which part of a conversation, including after switching provider (D193). The Gateway records the model and provider profile it sent with the request on each assistant message it stores (GAP-PAA-28, decided on the 2026-10-22 dev call). |
| D192 | Audit records use one portable, privacy-bounded envelope | Every action has a stable ID, timestamp, event, authenticated actor, action, outcome, and correlation ID, with optional resource, reason, and non-sensitive details. Retention, indexing, and presentation remain implementation choices. |
